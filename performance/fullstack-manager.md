# 绩效规则制定的流程

> 案例：全栈工程师绩效标准（profile/qttech/performance/fullstack-engineer.md）的制定过程。记录流程本身，供制定其他岗位标准时参照。

## 流程四步

### 1. 提出猜想

规则制定始于人的直觉判断，通常是真实问题带来的感觉。本次的原始感觉是：**接手前面阶段的工作时，发现交付接不住——产品也提不出具体方向，当时这块是由技术负责人负责的，所以问题在这里。**先把这个感觉如实记下来，不急着论证，也不急着归因。

猜想是低成本的：一句话就够。它的价值在于指明往哪里看——本次猜想直接把焦点从「执行岗干得如何」转向「负责人是否有责任」。

### 2. 找原始资料溯源

### 2. 找原始资料溯源

拿着猜想回到原始资料验证——**没带就是没写**：仓库里没有 tag 就是没发布，规范仓库没有提交就是规范缺位，测试目录没有新功能覆盖就是没覆盖。不以任何人的口头说明为准，包括负责人自己。

溯源的产出是绩效记录：只记事实与证据，不做归因。猜想可能被证实，也可能被推翻——两种结果都成立，推翻猜想同样有价值。

### 3. 反思判定依据

记录摆出来后，问题聚焦到负责人身上：产品提不出方向、技术自主推进无验证——**绩效的缺口首先在负责岗位，不在执行岗**。执行人交付了部署链路、安全基础、转赠机制，但没有任何一层被业务验证；这个结果首先是负责人的失职：接手时没有验收标准、没有期初约定、没有推动 beta 晋级。

因此先制定的是**负责岗位**的绩效标准（fullstack-manager：交付什么算数、如何建立验收与期初约定），而不是执行岗的。执行岗的标准（fullstack-engineer）随其后制定，其判定阶梯从属于负责人建立的验收框架。

把这个反思显性化的过程中暴露了模糊处——「代码还在主干算不算有效」「负责人未建立验收时执行岗的交付如何计」——模糊处就是标准要回答的问题。

### 4. 制定绩效规则

把反思出的判定逻辑写成岗位标准文件（profile/<产品>/performance/<岗位>.md），核心回答：**什么样的交付算数。**

标准必须包含：

- 有效性的判定条件（我们定为：被使用 / 被验收 / 被收编，三选一）
- 判定阶梯（判不出有效时归哪一档）
- 分项门槛（不同类别工作的差异）
- 判定锚点（期初约定，防止事后挪门柱）

标准是事后从案例中提炼的，条款是否站得住，等下一期工作按它走一轮再修订。跑过数期、不再频繁修订后，抽取共性升为章程。

本次制定的顺序是：负责人标准先行（fullstack-manager，本文档即为制定过程记录），执行岗标准随其后（fullstack-engineer）。

## 经验

- **猜想先行，溯源验证**。人的感觉指向真问题，原始资料提供证据，两者缺一不可——只有猜想是空转，只有资料是没有焦点。本次猜想同时修正了归因方向：问题首先在负责岗位。
- **责任向上找**。执行岗交付未经业务验证时，先检查负责人是否建立了验收标准与期初约定——没建立，缺口首先记在负责岗的绩效上，绩效标准也应先从负责岗位制定。
- **没带就是没写**。判定以原始资料为唯一依据，口头说明、记忆、意图都不算。
- **先记录，后标准，再章程**。跳过记录直接写标准，标准是想象出来的；跳过标准直接写章程，章程没有牙齿。
- **记录只管客观显性化**。原因分析、归因、改进建议都不进绩效记录——它们属于复盘报告。
- **标准的措辞要能被复述**。执行人读完应能说清「我的工作怎样才算数」。
- **一个岗位一份标准，逐岗位积累**。不要一次设计覆盖全公司的绩效体系。
