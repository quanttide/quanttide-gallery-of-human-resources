# 绩效规则制定的流程

> 案例：全栈工程师绩效标准（profile/qttech/performance/fullstack-engineer.md）的制定过程。记录流程本身，供制定其他岗位标准时参照。

## 流程五步

### 1. 从事实出发，不做归因

回到工作发生的仓库，收集客观证据：提交历史、tag、CHANGELOG、文件状态。产出**绩效记录**——只记交付事实与阶段状态，不分析原因、不评价人。

这一步的产物示例：`report/performance/qtcloud-pay-provider.md`。

### 2. 判定有效与无效

对着记录，逐个工作项判定：哪些被业务验证过（有效），哪些只是代码存在（未验证），哪些被重做（已重做）。

这一步会暴露判定标准本身的模糊处——比如「代码还在主干算不算有效」。把模糊处记下来，它们就是标准要回答的问题。

### 3. 把判定规则写成标准

把上一步实际使用的判定逻辑显性化为标准文件，放在岗位目录下（profile/<产品>/performance/<岗位>.md）。核心是回答一个问题：**什么样的交付算数。**

标准必须包含：

- 有效性的判定条件（我们定为：被使用 / 被验收 / 被收编，三选一）
- 判定阶梯（判不出有效时归哪一档）
- 分项门槛（不同类别工作的差异）
- 判定锚点（期初约定，防止事后挪门柱）

### 4. 用下一期工作校准

标准是事后从案例中提炼的，条款是否站得住，要等下一期工作按它走一轮：期初约定 → 执行 → 按标准判定 → 记录。站不住的条款修订，缺的补。

标准不是一次写成的，是记录与判定循环校准出来的。

### 5. 稳定后升章程

同类岗位的标准跑过数期、条款不再频繁修订后，抽取共性升为章程。此时章程有案例托底，不是空转的条文。

## 经验

- **先记录，后标准，再章程**。跳过记录直接写标准，标准是想象出来的；跳过标准直接写章程，章程没有牙齿。
- **记录只管客观显性化**。原因分析、归因、改进建议都不进绩效记录——它们属于复盘报告。混进来会破坏记录的公信力。
- **标准的措辞要能被复述**。执行人读完应能说清「我的工作怎样才算数」。做不到就还在堆概念。
- **规则制定本身要有成本意识**。一个岗位一份标准，逐岗位积累；不要一次设计覆盖全公司的绩效体系。
